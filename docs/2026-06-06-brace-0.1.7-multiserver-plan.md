# Plan: 0.1.7 — "Multi-server release"

Status: planning
Date: 2026-06-06
Owner: Matt

## Decision

**0.1.7 is the multi-server release.** We complete every outstanding horizontal-scaling
item — correctness blockers *and* the fleet-observability layer — before cutting the tag.
After 0.1.7, "Brace runs correctly behind a load balancer with N instances sharing one
Postgres" is a true, documented claim with no silent footguns.

Two scope decisions (made 2026-06-06):

1. **Scope = blockers + observability.** Not just behavioral correctness (B2/B4/B5/B6) but
   also Phase 3 (instance-tagged stats, fleet-aware dashboard/logs). Truly end-to-end.
2. **Default posture = automatic when Postgres is present.** If an app runs on Postgres,
   the multi-server-correct path is the default — no per-subsystem opt-in. Single-process
   apps (and the H2 test path) are unaffected because one instance is trivially consistent.
   The **shared cache backend stays separately opt-in** (`CacheBackend.postgres(...)`) — it
   has a real cost (serialization, a DB round-trip per read) that shouldn't be forced on
   apps happy with a per-process cache. Everything else (rate-limiter counter, ops
   login/secret, regression state, instance-tagged metrics) flips on automatically.

   *Rationale for the split:* the cache trades latency for consistency and many apps
   legitimately want the fast per-process default; the other subsystems are simply *wrong*
   at scale with no upside to staying per-process, so safe-by-default is correct.

## Source of truth

This plan operationalizes the audit in [`2026-06-04-brace-multi-server.md`](2026-06-04-brace-multi-server.md).

## Cross-cutting foundations

Most items reduce to the same two DB primitives. Build these once, reuse everywhere. Both
must work on **H2** (the `mvn test` path is single-process H2) as well as Postgres, except
the message bus (genuinely Postgres-only; falls back to in-process on H2/no-DB).

- **F1. Instance identity.** A stable per-process `instanceId` (e.g. `hostname + ":" + port
  + "-" + shortRandom`, computed once at startup, exposed via `Brace.instanceId()`). Needed
  by B6 (deploy/baseline anchoring), P3 (instance-tagged rows), and ops dashboards. Small.
- **F2. DB-backed counter with window/expiry.** Generalize the existing
  `CacheBackend.incr` pattern into a coordination counter the rate limiter (B4) uses
  without forcing the shared *cache*. Either a dedicated `brace_counters(key, window_start,
  n, expires_at)` table or reuse the cache-counters table behind a narrow internal API.
  Single atomic `INSERT … ON CONFLICT … DO UPDATE SET n = n + ? RETURNING n` (H2 supports
  `MERGE`/`ON CONFLICT` 2.x). Reuses B1's "derive the window slot from wall-clock" trick.

Advisory locks were deliberately avoided in B1 (row locks port to H2); keep that bias —
prefer table + `ON CONFLICT` claims over `pg_advisory_lock` so the test tier stays on H2.

## Migration & test conventions (apply to every item below)

- Framework migrations are **immutable** (see AGENTS.md). New behavior = **new** `V*` file
  under `src/main/resources/brace/db/migration/` (runs on H2 + PG) or `…/migration_pg/`
  (PG-only). Current max version is **V8**; next is **V9**, then V10, … assigned in the
  order items land.
- Every new migration → add its `name=sha256` line to
  `src/test/resources/framework-migrations.lock` (`FrameworkMigrationsFrozenTest` prints it).
- Cross-instance behavior that can't be exercised on single-process H2 (B2 fan-out, B4
  cluster-wide counting, B6 dedupe-across-boxes) gets a **Postgres testcontainer IT**
  (`*IT`, runs under `mvn verify`) that starts **two** `Brace` instances against one
  Postgres and asserts the shared behavior. This is the real proof the release rests on.

### B2 — WebSocket room fan-out across instances ⛔ *(biggest item)*

**Problem.** `WsContext.rooms` (`WsContext.java:17`) is a process-local static map;
`broadcast(room, msg)` (`WsContext.java:60-67`) only reaches sockets on the same box, so a
room silently splits into N disjoint sub-rooms behind an LB.

**Design.** Introduce a `MessageBus` interface with two implementations:
- `PostgresMessageBus` — one dedicated listener connection per instance (held outside the
  HikariCP request pool) running `LISTEN brace_ws`; `broadcast` issues
  `pg_notify('brace_ws', payload)`. Each instance's listener delivers to its **locally**
  connected room members (the existing in-memory `rooms` map becomes the local-delivery
  leg only). Payload = `{room, message}` JSON.
- `InProcessMessageBus` — no-op pass-through (current behavior) for single-process / H2 /
  no-DB apps. Selected automatically when there's no Postgres `DatabaseFactory`.

**Caveats to handle (from the audit's Decisions §1):**
- `pg_notify` payload caps at **8000 bytes** → spill larger messages to a
  `brace_ws_messages(id, payload, created_at)` row and notify the id; listeners fetch + then
  the row is reaped (TTL/retention sweep, mirror the ops_timeseries retention job).
- Delivery is **at-most-once, only to currently-connected listeners** — correct for
  ephemeral broadcast, explicitly *not* missed-message replay. Document that contract.
- The listener connection must auto-reconnect on drop (Postgres restart, network blip).

**Posture.** Automatic: Postgres present → `PostgresMessageBus`; else in-process.

**Migration.** V-next: `brace_ws_messages` spill table (PG-only is fine;
`InProcessMessageBus` needs no table). Listener uses raw JDBC (`db.jdbc(...)`), not Hibernate.

**Tests.** Two-instance Postgres IT: connect a WS client to instance A and another to
instance B, both `join("lobby")`; `broadcast("lobby", …)` on A must reach B's client.
Plus a >8KB payload test exercising the spill path, and a listener-reconnect test.

**Effort:** L. **Depends on:** F1 (instance id, minor). The one item needing a new Postgres
capability — start it early so it's not the long pole at release.

### B4 — Shared rate-limiter counter

**Problem.** `RateLimiter` (`RateLimiter.java:18,50-71`) counts per-process; a 100/min limit
across 4 boxes allows ~400/min. `CacheBackend.incr` is already a shared atomic counter but
the rate limiter doesn't use it, and we don't want to force the shared *cache* on apps.

**Design.** Give `RateLimiter` access to F2 (the DB-backed counter). When a `DatabaseFactory`
is present, the sliding/fixed-window count is a single atomic
`INSERT … ON CONFLICT (key, window) DO UPDATE SET n = n + 1 RETURNING n`; the limiter
decides allow/block on the returned cluster-wide count. No DB → current per-process path.
Key = `ratelimit:{scope}:{windowSlot}`; windowSlot derived from wall-clock (B1's trick), so
no coordination needed beyond the atomic upsert. Expiry column lets the retention sweep reap
old windows.

**Posture.** Automatic when Postgres present.

**Migration.** V-next: `brace_counters` (or reuse cache-counters table via F2). H2-compatible.

**Tests.** Two-instance IT: fire N requests split across both instances, assert the limit is
enforced cluster-wide (not N×). Unit test the window-slot math. Keep the existing
per-process test for the no-DB path.

**Effort:** M. **Depends on:** F2.

**Load & tuning:** counting on every request is real DB write load. The Postgres path uses a
single-statement `ON CONFLICT` upsert and the counter tables are `UNLOGGED` + low-fillfactor (HOT
updates) — trading durability we don't need (crash/failover reset is acceptable for ephemeral
counters) for speed. Residual cost (round trip, hot-key row serialization, pool coupling) and the
recommendation to use **Redis** (future, not yet implemented) for truly high load / hot keys are in
[`docs/2026-06-07-rate-limiter-load.md`](2026-06-07-rate-limiter-load.md).

### B5 — Ops console login behind a load balancer

**Problem.** Two compounding bugs (`OpsHandler.java:20-21,112-121`, `Brace.java:452`):
(a) single-use login token lives in box A's heap (`loginTokens` map) → the `exchange` call
routed to box B 401s; (b) the ops-token signing secret is **per-process random**
(`OpsToken.generateSecret()`), so even an issued ops cookie won't validate on another box.

**Design.**
- (a) Make the browser login token a **stateless short-lived HMAC** value (same construction
  `OpsToken` already uses — `base64url(json).base64url(hmac)` with a `nbf/exp`), signed with
  the shared ops secret. No server-side store → delete the `loginTokens` map entirely. (If we
  want single-use semantics, gate redemption with an `INSERT … ON CONFLICT DO NOTHING` into a
  tiny `brace_used_tokens(jti, exp)` table; otherwise short TTL is enough — decide during impl.)
- (b) Derive the ops-token signing secret from **shared config** (mirror how the session
  secret already works), not `generateSecret()`. Same secret on every box → cookies validate
  fleet-wide. Keep `generateSecret()` only as the dev/no-config fallback, and **warn at
  startup** when an ops-enabled app runs without a configured ops secret (it'll bounce at scale).

**Posture.** Automatic: if an ops secret is configured, it's shared; warn if not.

**Migration.** None required for the stateless path (optional `brace_used_tokens` if we want
strict single-use).

**Tests.** IT: issue a login token via instance A, redeem it on instance B → success. Ops
cookie minted by A validates on B. Startup-warning test for missing ops secret.

**Effort:** S–M. **Depends on:** ops-secret config plumbing (small).

### B6 — Regression dedupe / baseline / acknowledge

**Problem.** `RegressionTracker` keeps the seen-set, notify-once dedupe, acknowledge state,
and a per-JVM `AtomicLong` id **in heap** (seeded per-process). At N instances: a new error
fires N duplicate alerts; `/ops/regressions/{id}/acknowledge` only acks one box and the
numeric id means different things per box; rolling deploys make the same error a "regression"
on late boxes and "pre-existing" on early ones.

**Design.** Move detection *state* to a shared table keyed by a **stable** `(type, route,
deploy)` identity (not a per-JVM counter):
- `brace_regressions(id text/uuid PK, type, route, deploy_marker, first_seen, baseline,
  notified_at, acknowledged_at, acknowledged_by)`.
- **Notify-exactly-once** via atomic claim: `UPDATE … SET notified_at = now() WHERE id = ?
  AND notified_at IS NULL` (or `INSERT … ON CONFLICT DO NOTHING`); only the row-affecting
  instance sends the alert. The errors themselves are already DB-backed and fine.
- **Acknowledge** writes to the shared row → consistent across boxes; stable string id.
- **Baseline** anchored to a **shared deploy marker** (config/env, e.g. git sha or release
  tag), not `Instant.now()` per JVM — so a rolling deploy classifies an error identically on
  every box. This also gives F1/P3 a deploy dimension.

**Posture.** Automatic when Postgres present. (`a9c5b26` already wired server-side detection
+ notifiers; this swaps the in-memory state for the shared table.)

**Migration.** V-next: `brace_regressions`. H2-compatible.

**Tests.** Two-instance IT: same new error observed on A and B → exactly one alert fires;
ack on A is visible on B; baseline anchored to deploy marker survives staggered start.

**Effort:** M. **Depends on:** F1 (deploy marker / instance id), B5's shared-secret plumbing
is independent.

### P3 — Fleet observability

**Problem.** The whole `Stats` layer, `/ops/logs` (`LogTap` static deque), and
`JfrProfiler`/heap are per-box; the dashboard self-polls every ~5s and lands on different
boxes, so numbers flicker and an overloaded peer is invisible from a healthy one. The
`ops-flush-*` jobs `INSERT INTO ops_timeseries` from every box with **no instance label**, so
the timeseries is silently summed across the fleet.

**Design.** Make metrics instance-aware and the dashboard fleet-aware:
- **Instance-tag `ops_timeseries`.** New migration: `ALTER TABLE ops_timeseries ADD COLUMN
  instance_id text` (can't edit the original immutable migration). Flush jobs write F1's
  `instanceId`. Read paths aggregate across instances (sum/avg as appropriate) and offer a
  per-instance breakdown.
- **Dashboard.** Add an **instance picker / "all instances" aggregate** to
  `/ops/dashboard`; show which instances are live and their individual health, so a
  GC-thrashing or CPU-pegged box is visible. Resolve the self-poll flicker by aggregating at
  read time rather than hitting one random box.
- **`/ops/logs` & JFR.** These are inherently per-instance; **document** them as such and
  label responses with `instanceId`. The real multi-instance log answer is an external
  aggregator (stdout JSON already goes everywhere) — state that in P0/scaling doc rather than
  building log shipping into the framework.
- **User metrics.** `stats.counter("orders.placed")` etc.: with instance-tagged timeseries,
  the dashboard can sum them fleet-wide; clarify in docs that the live `/ops/status` number is
  this-box-only and the timeseries is the fleet view.

**Posture.** Automatic: flush jobs always write `instanceId`; dashboard aggregates by default.

**Migration.** V-next: `ops_timeseries` add `instance_id` (+ index for per-instance reads).
H2-compatible `ALTER TABLE ADD COLUMN`.

**Tests.** IT: two instances flush metrics → rows carry distinct `instance_id`; aggregate
read sums correctly; per-instance read filters correctly. Dashboard renders with the picker.
Migration test updates the lock file.

**Effort:** L. **Depends on:** F1. Largest UI surface; can proceed in parallel with B2.

## Sequencing

Parallelizable tracks once foundations exist:

1. **Now / parallel:** P0 contract doc (draft), F1 (instance id), F2 (DB counter).
2. **Track A (data/coordination):** B5 (S–M) → B4 (M, needs F2) → B6 (M, needs F1).
3. **Track B (the long poles):** B2 (L, start early) and P3 (L) in parallel — neither blocks
   the other; both lean on F1 and the testcontainer IT harness.
4. **Converge:** finalize P0 wording (flip "breaks" → "correct"); update the 0.1.7 migration
   guide and shared-cache guide language; run full `mvn verify` (H2 + two-instance PG ITs).
5. **Cut 0.1.7:** bump `pom.xml` off `-SNAPSHOT`, README `v0.1.6 → v0.1.7`, tag → auto-publish.

Rough total: 2 L items (B2, P3), 3 M (B4, B6, F2-ish), 2 S–M (B5, P0, F1). B2 and P3 dominate.

## Open questions (resolve during impl, not blocking the plan)

- **B5 single-use:** strict single-use (tiny `brace_used_tokens` claim table) vs. short-TTL
  stateless only? Lean stateless-only unless replay within the TTL is a real concern.
- **F2 table:** dedicated `brace_counters` vs. reuse `brace_cache_counters` behind an internal
  API? Dedicated is cleaner separation; reuse saves a table. Lean dedicated.
- **Deploy marker source (B6/P3):** explicit config (`deploy=<sha>`) vs. auto from a build
  stamp? Lean explicit config with a sane default.
- **P3 dashboard:** instance picker + aggregate is the floor; do we also want a compact
  "fleet strip" (one row per live instance)? Decide when building the UI.
